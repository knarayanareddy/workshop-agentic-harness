~1 min. Doc Ock: the harness is the arms and the control around the brain. The model alone only produces text; the harness gives it hands (tools), a memory (the messages it resends), a job description (system prompt) and limits (guardrails). Everyone in the room has used one; today you build one.
1 · What's an agent?

An agent is a running application

LLMdecides
+
Harnessacts and controls
=
Agenta process that is running

The agent is a model interacting with the real world through a harness.

~1 min. Stress that an agent is not a model or a file; it is an application that is running, like any other program. It starts, holds state (the messages), calls the model in a loop, runs tools, and stops. An LLM alone is a function; a harness that is not running does nothing. The loop itself comes back in section 3.
1 · Why build your own harness

Why not just use Claude Code?

A generic harness is built for every project. Your own gives you control of:

What the agent knows
How the agent behaves
How the agent gathers information and executes actions
What the agent shouldn't do
~2 min. Claude Code is excellent, and you can extend it (CLAUDE.md, skills, hooks), but only at the points it offers. In your own harness every point is yours. And building one is the fastest way to understand what any agent does under the hood. Context: what the model sees. Behavior: how the agent acts. Information and actions: what it can read and do. Guardrails: what is blocked, gated or enforced.

2 · Context engineering

Offer useful tools

object ChordsInKey : Tool {
    override val name = "chords_in_key"
    override val description = "Diatonic chords of a key. mode: major or minor."
    override val inputSchema = JsonSchema.obj()
        .string("key", "Root note, e.g. C or F#")
        .string("mode", "major or minor").build()

    override fun execute(input: ToolInput, ctx: ToolContext): ToolOutcome {
        val root = NOTES.indexOf(input.string("key"))
        if (root < 0) return ToolOutcome.Failure("Unknown key. Try: $NOTES")
        val scale = if (input.string("mode") == "major") MAJOR else MINOR
        val chords = scale.map { (s, k) -> NOTES[(root + s) % 12] + k }
        return ToolOutcome.Success(chords.joinToString(" | "))
    }
}

C major: C | Dm | Em | F | G | Am | Bdim. The theory is code; the model only decides when to call it.

A generic model often gets chords wrong, especially in less common keys. The tool holds the theory as code: deterministic and cheap; the model only decides when to call it. Input: key and mode (major or minor). An unknown key returns a Failure, which the model reads and corrects. NOTES, MAJOR and MINOR are constants left out of the slide; MAJOR and MINOR are (step, chord kind) pairs.
3 · The agentic loop

The loop

~3 min. Runs by itself; follow the numbers. 1: the system prompt and the messages go to the model. 2: one inference call. 3: the model answers with a tool use. 4: the harness runs the tool; guardrails check before and after. 5: the result is appended to the messages, back to 1. Two loops here, then 6: the model answers with end_turn and the response comes out. The animation then restarts.
3 · The agentic loop

The same loop in code

for (iteration in 1..config.maxIterations) {
    val response = model.infer(request)                         // 2
    history += Message.assistant(response.content)

    when (response.stopReason) {
        StopReason.ToolUse ->                                   // 3
            history += Message.user(toolUses.map(::executeToolUse)) // 4, 5
        StopReason.EndTurn ->                                   // 6
            return AgentResult.Completed(history.last().text)
    }
}
return AgentResult.LimitReached("maxIterations")

7 · Guardrails

Why build your own: What the agent shouldn't do

Protect against
unwanted behavior

What a guardrail does

Preventaction is blocked
Gatehuman approves first

Why it holds

Enforcethe agent cannot ignore it

In the workshop Assignment 4: never push to OpenRA, no Python, don't take orders from files, keep secrets secret. · guardrails/exercise/

~3 min. A guardrail does two things. Prevent: the action is blocked, nobody decides. Gate: the action pauses and the human decides. Enforce is not a third action but the property of both: the check runs in the harness, outside the model, so the agent cannot ignore or talk its way around it. A system prompt instruction is advisory; the model can skip it. A guardrail can also require something, e.g. beforeEndTurn returns Continue until the tests have run.
7 · Guardrails

Four hooks

interface Guardrail {
    fun beforeInference(ctx)            // Proceed | Abort
    fun beforeToolUse(call, ctx)        // Allow | Ask | Deny
    fun afterToolUse(call, result, ctx) // Accept | Replace | Reject
    fun beforeEndTurn(ctx)              // AllowEnd | Continue
}

All hooks have defaults. Implement the one you need.

7 · Guardrails

CommandGuardrail

override fun beforeToolUse(call: ToolCall, ctx: TurnContext): ToolDecision {
    val command = call.input.string("command")
    if (NEVER.any { it.containsMatchIn(command) })
        return ToolDecision.Deny("never allowed")        // Prevent
    return if (isReadOnly(command)) ToolDecision.Allow
    else ToolDecision.Ask("runs: $command")              // Gate
}

Do you need skills?

~1 min. Skills are how you extend an agent whose code you cannot change, like Claude Code. In your own harness you add the prompt section or tool directly.
8 · Skills

Tool or skill?

ToolSkill
What it isCode the harness runsInstructions the model reads
Gives the modelA result: data, or an action doneKnow-how: how to do a task
Always in contextName, description, schemaName and a one-line description
Loaded when usedThe resultThe full instructions
Holds?Yes: the code does what it doesAdvisory, like the system prompt

Use a tool when the answer can be computed. Use a skill when the model needs to know how.

~1.5 min. Both are chosen by the model, based on a short description that is always in context. The difference is what comes back: a tool returns a result that code produced, a skill returns text the model should follow. Putting all situational instructions in the system prompt dilutes the model's attention on the rest (and costs tokens, though caching softens that). Loading them only when needed is the skill idea.
8 · Skills

A skill is a tool that returns instructions

object LoadSkill : Tool {
    override val name = "load_skill"
    override val description =
        "Load the instructions for a task before you start it. " +
        "Skills: lua_mission (write a mission), new_unit (add a unit)."
    override val inputSchema = JsonSchema.obj()
        .string("name", "Skill name").build()

    override fun execute(input: ToolInput, ctx: ToolContext): ToolOutcome {
        val name = input.string("name")
        return ToolOutcome.Success(ctx.workspace.readText("skills/$name.md"))
    }
}

The description lists the skills; the body is only loaded when the model asks for it.

~1 min. Not in the default harness and not an assignment, but a good one for "What tool would you build?" in assignment 3 extra.
