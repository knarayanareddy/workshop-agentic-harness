Teach an agent to mod Red Alert

You get a small, working coding agent and a real game to point it at: OpenRA, the open-source remake of Command & Conquer: Red Alert. Over the next hours you extend the agent until it can find its way around OpenRA, change the game safely, and prove that its changes still build.

OpenRA is a large C# code base. Its units, weapons and factions are defined in YAML rules, and its missions are scripted in Lua. That's too big to fit in a model's context and too easy to break by guessing, which is why it suits this workshop. The model can't hold all of OpenRA at once. Your job is to decide what it sees and what it may do. You'll do that with three things:

ToolsWhat the agent can do. The model reads only the description.
System promptAlways in context. Always paid for. Advisory.
GuardrailsEnforced by the harness. The model can't skip them.

PieceWhereWhat it does

The workspace folder

workspace/ is the agent's sandbox. When you start the harness it works on this folder, and every path the agent uses is relative to it. Inside you'll find:

workspace/
├── README.md     what this folder is for
├── docker/       the OpenRA toolbox: build, check, package
├── OpenRA/       the game's source; not there yet, the agent clones it in assignment 1
└── out/          playable builds, written by the toolbox
  • The agent can't leave it. The file tools resolve every path inside workspace/ and refuse anything that escapes, including ../ tricks and symlinks that point outside. This isn't a guardrail. The tools are built so they can't do it, which is the strongest kind of safety there is.
  • It's yours to break. Everything in it except README.md and docker/ is git-ignored. If the agent makes a mess of OpenRA, put it back the way it was cloned with git -C workspace/OpenRA reset --hard && git -C workspace/OpenRA clean -fd.
  • You can point it elsewhere. ./gradlew :app:run --args="path/to/a/project" makes another folder the workspace.

The guardrails that are already on

A guardrail is code in the harness that checks every step of the agent and can stop it. Unlike an instruction in the prompt, the model can't talk its way past one. The harness ships with four, and you'll see them in the trace as guard lines:

GuardrailJobWhat it does
protected-pathsPreventBlocks .env files, .git/ internals and private keys, including when a shell command names them.
commandPrevent + GateLets read-only commands like ls, cat and git status through. Never allows rm -rf, git push or git reset --hard. Every other command waits for your approval.
build-filePrevent + GateNever lets the agent edit build files such as build.gradle.kts or package.json. Asks you before it writes a file outside a src/ folder.
result-capRewriteCuts any tool result over 30,000 characters and tells the model to ask for less, so one huge file can't flood its context.

When a guardrail wants your approval, the agent pauses:

!! run_command needs approval:
   - runs a command: git clone ...
   input: {"command":"git clone ..."}
   [y] approve  [a] always for run_command  [n] deny >

y approves this one call, a approves this tool for the rest of the session, and n denies it. You can give a reason, and the model reads it.

Read the guardrails in guardrails/defaults/ in your language before assignment 4. You'll write your own next to them.

TypeScript runs inside the JVM, in an embedded JavaScript engine. async works, but there is no event loop: no setTimeout, fetch or Node.js modules. Read and write files through ctx.workspace.
Why it works this way: the harness is a Kotlin program, and it runs your bundle in GraalJS, a JavaScript engine that lives inside the JVM. The agent loop calls your function and waits for its answer. When you return a Promise, the harness waits only until the code that is already running finishes. Nothing ever runs a timer or waits for the network, so a Promise that depends on one never settles. Your values don't stay JavaScript objects: they reach Kotlin as JSON. So return plain data, not class instances.

Reference

The loop, in one page

This is everything the harness does. Every extension you write plugs into one of these points.

user message → append to messages[]
  → Guardrail.beforeInference        (inspect / rewrite / abort)
  → model inference
  → stop_reason?
      ├─ tool_use → Guardrail.beforeToolUse   → Allow | Deny | Ask
      │           → execute tool
      │           → Guardrail.afterToolUse    → Accept | Replace | Reject
      │           → append tool_result → back to model inference
      └─ end_turn → Guardrail.beforeEndTurn   → AllowEnd | Continue
                  → final response, or back to model inference

Where you put a rule decides whether it holds

WhereExampleGuarantee
System prompt"Always run the tests before reporting done"Advisory. Always in context, always paid for.
Toolrun_tests returning pass/fail and outputA capability only. The agent chooses whether to call it.
GuardrailafterToolUse runs the linter and rejects on failureEnforced. The model can't skip it.

The three jobs of a guardrail

JobHookDecisionEffect
PreventbeforeToolUseDeny(reason)The tool never runs. The model gets an error result.
GatebeforeToolUseAsk(reason)The human approves or denies.
EnforceafterToolUseReject(feedback)The result becomes an error and goes back to the model.
beforeEndTurnContinue(message)The turn may not end yet.

Look under the hood

The trace shows a summary of every step. Two tools show you more.

  • /report: type it at the > prompt. It writes the current session as an HTML page to reports/session-<timestamp>.html: every message, every tool call with its input, result and duration, the guardrail and approval decisions on each call, and the billed tokens and cache hits per inference. Open it in your browser to see what the model actually got back from your tools.
  • MODEL_LOG_RAW: set this environment variable (any value) before you start the agent, and every raw request and response body to and from the model is printed to stderr. That is the whole context as the model sees it: the system prompt your sections built, the tool schemas, and the full history, resent on every call.

Where am I?

When the harness starts, have it find out the date and time, the operating system, and whether the workspace is in a git repository. Tell the model in a Static system prompt section called environment.

Why are we doing this?

Every session starts blind. The model assumes the date of its training data, guesses which commands work on your system, and spends tool calls, each one waiting for your approval, to find out the rest. The harness can check all of it once at start-up, for free.

package com.jdriven.harness.extensions.kotlin.systemprompt.exercise

import com.jdriven.harness.api.SystemPromptSection
import com.jdriven.harness.api.Workspace
import com.jdriven.harness.extensions.kotlin.helpers.Git
import com.jdriven.harness.extensions.kotlin.helpers.Host

/** What the harness finds out about where it runs, once at start-up. Static: none of it changes during the session. */
object Environment {
    fun section(workspace: Workspace): SystemPromptSection {
        val repository = Git.repositoryRoot(workspace)
        val git = if (repository != null) "the workspace is inside the git repository at $repository."
        else "the workspace is not in a git repository, so git cannot undo changes."
        return SystemPromptSection.Static(
            "environment",
            """
                # Environment
                - The session started at ${Host.now()}.
                - The system is ${Host.system()}. Commands run in ${Host.shell()}.
                - Git: $git
            """.trimIndent(),
        )
    }
}

Assignment 1.2 · Harness initialization

Is OpenRA there?

When workspace/OpenRA/ is missing, have the harness tell the model to either tell the user or clone it. Once it's there, the model hears nothing more. Use a Dynamic system prompt section called openra_checkout.

Why are we doing this?

The agent can't work on code that isn't there. The default WorkingAgreementsworkingAgreements.ts already has a rule for this, but that rule is in every inference call, even once OpenRA is there. The model also has to look before it knows, and all it can do is refuse. A Dynamic section only costs tokens while OpenRA is missing.

The clone command

Put this exact command in your section, so the model doesn't have to guess it:

git clone --depth 1 --config core.autocrlf=false https://github.com/OpenRA/OpenRA.git OpenRA

--depth 1 matters: a full clone of OpenRA is huge and won't finish within the 120-second limit of run_command. autocrlf=false keeps the scripts working in the Docker toolbox on Windows.

How does a Dynamic section work?

The harness calls it before every inference call. Text is added to the conversation as <context section="...">, and only when it has changed. null adds nothing. A Static section would still be saying "OpenRA is missing" after the clone.

Tell the user, or clone it?

Either is fine. If you choose to clone, the default command guardrail asks your approval before git clone runs, so the user still decides.

Everything the agent does with OpenRA goes through the toolbox: building it, checking it, packaging it. Done with run_command, that's a long docker command line, an approval prompt for each one, and a build that takes longer than the 120-second limit. A tool turns all of that into one call. It also teaches the first rule of tools: a tool call must not wait for minutes.

Writing the description

The model reads only the description. It's the tool's API documentation. Say what the tool does, what it needs, how long it takes and what to call next. A Failure is not a crash: the model reads the message and reacts, so make it say what to do ("Docker is not running. Ask the user to start it.").

Work that takes minutes

A tool call must not wait for minutes, so start does the Docker work in the background and writes its output to a log file, out/toolbox.log. status reads that log. What the model hears in each state is up to your tools.

Why no approval prompt?

Guardrails like command look at run_command. Your tool runs commands that you wrote, with no free text from the model in them, so there's nothing to approve. That's why a narrow tool is safer than a shell, and why you should keep its inputs narrow.

object ActorRules : Tool {

    override val name = "actor_rules"
    override val description =

/**
 * Denies running code straight from the internet: nobody has read it, and it runs with the user's permissions.
 * Any command that both downloads and runs is denied, piped or not: downloading and running are two steps.
 */
class PipeToShellGuardrail : Guardrail {
    override val name = "pipe-to-shell"

    override fun beforeToolUse(call: ToolCall, ctx: TurnContext): ToolDecision {
        val command = Commands.of(call) ?: return ToolDecision.Allow
        val names = Commands.names(command)
        val downloadsAndRuns = names.any { it in DOWNLOADERS } && names.any { RUNNERS.matches(it) }
        if (!downloadsAndRuns && !command.contains("DownloadString", ignoreCase = true)) return ToolDecision.Allow
        return ToolDecision.Deny("Running a script straight from the internet is never allowed. Download it to a file, show it to the user, and let them decide.")
    }

    private companion object {

import com.jdriven.harness.api.AgentEventListener
import com.jdriven.harness.api.ToolInput
import com.jdriven.harness.api.ToolOutcome

/** One line per turn on what the agent actually did, straight from the events rather than from its own summary. */
class TurnSummary : AgentEventListener {
    private val calls = linkedMapOf<String, Int>()
    private val changed = linkedSetOf<String>()
    private var denied = 0
    private var pending: AgentEvent.ToolCallProposed? = null

    override fun onEvent(event: AgentEvent) {
        when (event) {
            is AgentEvent.ToolCallProposed -> {
                pending = event
                calls.merge(event.toolName, 1, Int::plus)
            }
            is AgentEvent.GuardrailDecision -> if (event.decision.startsWith("Deny")) denied++
            is AgentEvent.ApprovalRequested -> if (event.decision.startsWith("Deny")) denied++
            is AgentEvent.ToolCallCompleted -> {
                val call = pending?.takeIf { it.toolName == event.toolName } ?: return
                if (event.outcome is ToolOutcome.Success && call.toolName in WRITES) changed += target(call)
            }
            is AgentEvent.TurnEnded -> {
                val tools = calls.entries.joinToString { "${it.key} ${it.value}" }
                println("[summary] ${calls.values.sum()} tool calls ($tools), $denied denied. Changed: ${changed.ifEmpty { setOf("nothing") }.joinToString()}")
                calls.clear()
                changed.clear()
                denied = 0
            }
            else -> {}
        }
    }

    private fun target(call: AgentEvent.ToolCallProposed): String {
        val input = ToolInput(call.input)
        return input.stringOrNull("path") ?: "${input.stringOrNull("actor")} (${call.toolName})"
    }

    private companion object {
        val WRITES = setOf("write_file", "edit_file", "set_actor_value")

import com.jdriven.harness.api.AgentEventListener;

import java.util.LinkedHashMap;
import java.util.LinkedHashSet;
import java.util.Map;
import java.util.Set;
import java.util.stream.Collectors;

/** One line per turn on what the agent actually did, straight from the events rather than from its own summary. */
public final class TurnSummary implements AgentEventListener {
    private static final Set<String> WRITES = Set.of("write_file", "edit_file", "set_actor_value");

    private final Map<String, Integer> calls = new LinkedHashMap<>();
    private final Set<String> changed = new LinkedHashSet<>();
    private int denied;
    private AgentEvent.ToolCallProposed pending;

    @Override
    public void onEvent(AgentEvent event) {
        if (event instanceof AgentEvent.ToolCallProposed e) {
            pending = e;
            calls.merge(e.getToolName(), 1, Integer::sum);
        } else if (event instanceof AgentEvent.GuardrailDecision e) {
            if (e.getDecision().startsWith("Deny")) denied++;
        } else if (event instanceof AgentEvent.ApprovalRequested e) {
            if (e.getDecision().startsWith("Deny")) denied++;
        } else if (event instanceof AgentEvent.ToolCallCompleted e) {
            if (pending != null && pending.getToolName().equals(e.getToolName())
                    && e.getOutcome() instanceof ToolOutcome.Success && WRITES.contains(e.getToolName())) {
                changed.add(target(pending));
            }
        } else if (event instanceof AgentEvent.TurnEnded) {
            String tools = calls.entrySet().stream().map(c -> c.getKey() + " " + c.getValue()).collect(Collectors.joining(", "));
            int total = calls.values().stream().mapToInt(Integer::intValue).sum();
            System.out.println("[summary] " + total + " tool calls (" + tools + "), " + denied + " denied. Changed: "
                    + (changed.isEmpty() ? "nothing" : String.join(", ", changed)));
            calls.clear();
            changed.clear();
            denied = 0;
        }
    }

    private static String target(AgentEvent.ToolCallProposed call) {
        ToolInput input = new ToolInput(call.getInput());
        String path = input.stringOrNull("path");
        return path != null ? path : input.stringOrNull("actor") + " (" + call.getToolName() + ")";
    }
}

src/listeners/exercise/turnSummary.ts

import type { AgentEvent, AgentEventListener } from "@harness/api";

const WRITES = new Set(["write_file", "edit_file", "set_actor_value"]);

/** One line per turn on what the agent actually did, straight from the events rather than from its own summary. */
export const turnSummary = (): AgentEventListener => {
  const calls = new Map<string, number>();
  const changed = new Set<string>();
  let denied = 0;
  let pending: Record<string, any> | null = null;
  return (event: AgentEvent) => {
    const e = event as Record<string, any>;
    switch (event.type) {
      case "tool_call_proposed":
        pending = e;
        calls.set(e.toolName, (calls.get(e.toolName) ?? 0) + 1);
        break;
      case "guardrail_decision":
      case "approval_requested":
        if (String(e.decision).startsWith("Deny")) denied++;
        break;
      case "tool_call_completed":
        if (pending && pending.toolName === e.toolName && e.outcome.kind === "success" && WRITES.has(e.toolName)) {
          changed.add(pending.input.path ?? `${pending.input.actor} (${e.toolName})`);
        }
        break;
      case "turn_ended": {
        const tools = [...calls].map(([name, n]) => `${name} ${n}`).join(", ");
        const total = [...calls.values()].reduce((a, b) => a + b, 0);
        console.log(`[summary] ${total} tool calls (${tools}), ${denied} denied. Changed: ${changed.size ? [...changed].join(", ") : "nothing"}`);
        calls.clear();
        changed.clear();
        denied = 0;
      }
    }
  };
};

Which shader?

glsl/combined.frag draws almost everything: terrain, units and the interface. Near the end it sets fragColor = c;. Change c just before that line.

The game won't start

The shader didn't compile. OpenRA writes the error to its log folder: ~/Library/Application Support/OpenRA/Logs on macOS, ~/.config/openra/Logs on Linux, %APPDATA%\OpenRA\Logs on Windows. Your workspace-only guardrail from 4.6 won't let the agent read it, so paste the error into the chat. Or build a tool for it in assignment 7.

Solution

In glsl/combined.frag, just before fragColor = c; in the else branch at the end:

		// An old film: grey everything, and darken every other row of pixels.
		float grey = dot(c.rgb, vec3(0.299, 0.587, 0.114));
		c.rgb = vec3(grey) * (mod(gl_FragCoord.y, 2.0) < 1.0 ? 0.8 : 1.0);

		fragColor = c;

For night vision, try c.rgb = vec3(0.1, grey * 1.4, 0.1); instead.
